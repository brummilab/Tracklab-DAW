# M1-05: Autosave, rotierende Backups, Crash-Recovery

Meilenstein: M1 · Design: Rev 3, §3 „Projektformat“ (E41) · Agent: test-writer → implementer · Abhängig: M1-04

## Fakten
- E41: Autosave alle 2 min (einstellbar) in `<Projekt>.tracklab.autosave`, nur wenn geändert; beim Speichern 10 rotierende
  Backups in `Backups/` (`<Projekt>.<JJJJMMTT-HHMMSS>.tracklab`, älteste zuerst löschen); einstellbar.
- Beim Öffnen: Autosave neuer als Projektdatei → Ergebnis `recovery_available` mit Zeitstempeln; Command
  `project.restore_autosave` (destructive) bzw. `project.discard_autosave`. Sauberes Speichern/Schließen löscht die Autosave.
- `project.list_backups` (readOnly), `project.restore_backup` (destructive, Parameter Backup-Name) – Wiederherstellen legt
  vorher ein Backup des aktuellen Stands an.
- Autosave als Message-Thread-Timer; schreibt atomar wie M1-04; respektiert `isSaveInhibited()`; Testbar mit
  injizierbarer Uhr/Intervall.
- Korrupte Projektdatei (M1-04 `corrupt_project`) → Fehler nennt die neueste Backup-/Autosave-Datei.

- Aus Review M1-04: beim Öffnen liegengebliebene `<Name>_temp*.tracklab` aufräumen; Ordner nach dem Ersetzen per fsync
  sichern (optional, Linux); `getParameterControlMappings().saveToEdit()` beim Speichern (sobald MIDI-Learn existiert);
  Projektnamen auf eine sichere Länge begrenzen (> 255 Byte führt heute zu `save_failed` statt `invalid_project_name`).

## Lead-Entscheidungen nach Test-Writer (09.10.2026)
1. Alle vom Test-Writer gepinnten Varianten gelten: Backup = Stand vor dem Speichern (Kopie der alten Datei), `new`
   ohne Backup; `recovery_available` als Schlüssel im Erfolg von `open`; Restore nur in den Speicher (modified, Undo leer,
   Datei erst beim Speichern); `discard_autosave` destructive; bei offener Recovery schreibt Autosave nicht.
2. Namenslänge: höchstens **120 Byte UTF-8** (Platz für Backup-Suffix und `.autosave` unter 255 Byte); Test an der Grenze.
3. `project.close` mit `discard:true` löscht die Autosave (destruktiv bestätigt); Test.
4. Speichern bei offener Recovery löscht die Autosave und beendet die offene Entscheidung; Test.
5. `restore_backup`: Name mit `/`, `\`, `..` oder absolut → `invalid_params`; unbekannter Name → `backup_not_found`;
   `discard_autosave` ohne Autosave → `no_autosave`. Tests.
6. Liegengebliebene Temp-Reste der Autosave beim Öffnen ebenfalls aufräumen; Test.
7. Builds parallel zu M1-07: `CMAKE_BUILD_PARALLEL_LEVEL=2` (OOM-Gefahr), eigenes `GATE_BUILD_DIR`.

## Lead-Entscheidungen nach Review Runde 1 (09.10.2026)
1. **Pfadlänge (Blocker 1/Muss 2):** Kein Verlass auf Windows-Long-Paths (Registry-Schalter ist standardmäßig aus).
   `project.new`/`save_as` prüfen auf **allen** Plattformen gleich, dass der längste abgeleitete Pfad (Backup-Datei inkl.
   Zeitstempel, Zählersuffix und Temp-Suffix; Autosave inkl. Temp) höchstens **259 UTF-16-Zeichen** hat; sonst neuer
   Fehlercode `path_too_long` (Meldung: kürzerer Name oder Ordner), nichts angelegt. Die 120-Byte-Grenze bleibt.
   Tests rechnen die erlaubte Länge aus der Länge des Testwurzelordners aus (genau an der Grenze ok, ein Zeichen mehr →
   `path_too_long`), damit sie unter Linux und Windows gleich laufen. Der 120-Byte-Test prüft die Byte-Regel
   unabhängig vom Pfad.
2. **Muss 3:** `restoreBackup` lässt das gewählte Backup nie wegrotieren; Test mit 10 Backups, ältestes wiederherstellen.
3. **Muss 13:** Doku korrigieren, Export neu erzeugen.
4. **Hinweis 4:** Existiert der Backup-Name schon (gleiche Sekunde), nicht überschreiben, sondern Zählersuffix

5. **Hinweis 6:** Temp-Reste in `Backups/` beim Öffnen mit aufräumen (enges Muster wie im Projektordner). Test.
6. **Hinweis 7:** Abweichung angenommen – `close discard:true` lässt die Autosave bei **offener** Recovery liegen;
