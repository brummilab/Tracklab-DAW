# O-09: JUCE-UndoManager – veralteter Redo-Stash (Upstream-Meldung, dauerhafte Lösung)

Meilenstein: direkt nach M1 (F44-Default) · Agent: researcher, danach implementer · Herkunft: Review M1-03 Runde 1/2, F44

## Fakten
- JUCE 9.0.3 `UndoManager::moveFutureTransactionsToStash` leert `stashedFutureTransactions` nur, wenn Redo-Einträge
  existieren; `undoCurrentTransactionOnly` hängt den Stash immer wieder an (juce_UndoManager.cpp:170–199, 350–359).
  `clearUndoHistory()` leert ihn nicht.
- M1-03 (Zwischenlösung): `Transaction::rollback()` vergleicht den Redo-Stack mit dem Stand bei Beginn; weicht er ab
  (Stash veraltet), wird die **gesamte Undo-Historie verworfen** – kein Geister-Redo, aber Historienverlust im Fall
  „Undo, neue Änderung, später scheitert ein Command nach Schreibzugriff“.

## Auftrag

   abwarten. Empfehlung als F-Frage.
3. Danach Rollback ohne Historienverlust umsetzen; Test „Historie bleibt erhalten“.
4. `executeBatch` prüft alle Command-IDs und Parameter vor dem ersten Schritt (Review M1-03 R2).
5. Annahme „Redo-Stack unverändert innerhalb offener Transaktion“ absichern (jassert/Doku); Doku `rollback` vs. `isOpen`.

## Lead-Entscheidungen nach Test-Writer Teil B (09.10.2026)
1. Fehleradresse bleibt wie bisher: `BatchResult::failedIndex` + params-relativer Pointer (kein `/steps/<i>/…`).
2. Die Vorabprüfung umfasst alles, was ohne Ausführen prüfbar ist: unbekannte ID, Schema der Params, `no_edit` für
   undoable Schritte ohne Edit. Gemeldet wird der Fehler mit dem kleinsten Schritt-Index (Beispiel: undoable Schritt 0
   ohne Edit + unbekannter Schritt 1 → `no_edit`, Index 0). Ein Test dazu ergänzt der Implementer.
3. `jassert` (Redo-Stack unverändert innerhalb offener Transaktion) und Doku `rollback` vs. `isOpen` setzt der
