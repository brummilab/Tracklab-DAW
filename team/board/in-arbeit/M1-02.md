# M1-02: Command-Registry v1 mit Schema-Validierung und Export

Meilenstein: M1 · Design: Rev 3, §3 „Registry v1“, §4 (Tool-Namen) · Agent: test-writer → implementer · Abhängig: M1-01

## Fakten
- DESIGN Rev 3 §3 und `team/research/m1-fundament/NOTIZEN.md` §4. Abhängigkeiten als Submodule mit festem Tag:
  nlohmann/json `v3.12.0`, pboettch/json-schema-validator `2.4.0` (beide MIT) unter `third_party/`.
- `core::Command` (id, titleDe, descriptionEn, paramsSchema, resultSchema, flags `readOnly|undoable|destructive|longRunning`,
  shortcut, menuPath, handler), `core::CommandRegistry` (registrieren, auflisten, ausführen mit Validierung von Parametern
  **und** Rückgabe, strukturierter Fehler `{ok:false,error:{code,message,pointer}}`).
- Schema-Subset-Regel als Test: nur `type, properties, required, additionalProperties(false), enum, minimum, maximum,
  items, anyOf, $ref, $defs, description, default`; jedes Objekt mit `additionalProperties:false`.
- Tool-Name = ID mit `_` statt `.`; Rückabbildung über Map; Kollision oder ungültiger Name (`^[a-zA-Z0-9_-]{1,128}$`) → Fehler.
- Export: Funktion erzeugt `tools.json` (Name, Beschreibung, Schema) und `docs/commands.md` (Deutsch, Tabelle je Namespace);
  CLI-Anbindung folgt in M1-07 – hier eine Test-Hilfe, die vergleicht, ob die eingecheckten Dateien aktuell sind.
- In M1-02 registrierte Commands nur zum Test (`app.version` readOnly). Ausführung auf dem Message-Thread (Assert).
- **Mini-Spike in der Karte:** Fehlertexte von pboettch für 5 Fälle (falscher Typ, fehlendes Pflichtfeld, Zusatzfeld,
  enum, Bereich) im Bericht zeigen – sie gehen später an Claude.

## Lead-Entscheidungen nach dem Test-Writer (08.10.2026)
Tests: Branch `worktree-agent-a44b4519da2b82a3c` (`13bd983`, `106d82b`, `1833acd`), 66 Fälle (62 rot gegen Stubs).
Schnittstelle in `src/core/*.h` verbindlich; Mini-Spike-Ergebnis zu den Fehlertexten im Test-Writer-Bericht.
1. Command-IDs: **mindestens zwei** Segmente, je `[a-z][a-z0-9_]*`; drei und mehr erlaubt.
2. ID > 128 Zeichen → `invalid_tool_name` – bestätigt.
3. Fremder Thread → `{ok:false, code:not_on_message_thread}` ohne Handler, vor `unknown_command`; **kein** `jassert`.
4. **Fehlertexte anreichern (für Claude):** fehlendes Pflichtfeld und unzulässiges Zusatzfeld bekommen den Pointer
   **auf das Feld** (`<objekt>/<name>`), nicht auf das Objekt; Messages nennen erwarteten Typ, erlaubte enum-Werte bzw.
   Grenzen (z. B. „expected number ≤ 12, got 99“). Die betroffenen Erwartungen der Tests (Pointer bei Pflicht-/Zusatzfeld)
   passt der Implementer an – ausdrücklich erlaubt, im Bericht auflisten.
5. Registrierungs-Pointer `/id`, `/handler`, `/paramsSchema/…`, `/resultSchema/…` – bestätigt.
6. Schema-Subset zusätzlich: `type` nur als einzelner String; hängende `$ref` → `invalid_schema`; `required`-Namen müssen
   in `properties` stehen → `invalid_schema`. Der Implementer ergänzt Tests dafür.
7. Werfender Handler → `{ok:false, code:handler_failed, message}` (std::exception abfangen); unzulässige Flag-Kombination
   (`readOnly` zusammen mit `undoable` oder `destructive`) → Registrierungsfehler `invalid_flags`. Tests ergänzen.
8. Exporttexte von `app.version` („Version anzeigen“ / „Returns the version of Tracklab.“) bleiben; `tools.json`-Format
   `{name, description, input_schema}` bestätigt.
